- [ ] When the first *cobalt* release after 5.0.0 reaches CRAN, pass the candidate weights to `cobalt::bal.compute()` as one matrix instead of one column at a time. That release lets `bal.compute()` take a matrix of weights (one column per set of weights) and return one value per column. For `energy.dist`, `kernel.dist`, `distance.cov`, and `distance.cor`, it computes every column in a single matrix product, which is faster than `apply()` and avoids `future.apply::future_apply()` copying the n x n matrix in the `bal.init()` object to every worker (about 500MB per worker with 8000 units). The call sites are the `apply()`/`future_apply()` pairs in `R/weightit2gbm.R` (currently lines 591/594, 639/642, 995/998, and 1033/1036) and `apply(w_mat, 2L, cobalt::bal.compute, x = init)` in `R/weightit2super.R` (currently lines 684 and 749). For the other statistics, `bal.compute()` loops over the columns sequentially, so the `future_apply()` path may still be faster for them when a parallel plan is set; benchmark before removing it. Raise the *cobalt* requirement in `DESCRIPTION` to that release, and check *cobalt*'s NEWS for its version number.

- [x] Add `hatvalues()` methods for `ordinal_weightit` and `multinom_weightit` objects, following `_dev/hatvalues-ordinal-multinom.md`, so *adrftools* can use the HC2 adjustment for them. They return the generalized leverage \(\mathrm{tr}(F^{-1} F_i)\) from the expected information (reusing `.multinom_info()` and `.ordinal_info()`), and match `VGAM::hatvalues()` summed across columns, a brute-force trace, and `glm()` with two categories. Tests in `test-hatvalues.R`; documented on `?glm_weightit-methods`; NEWS item added. A leverage can exceed 1 (up to the number of categories minus 1), in which case *adrftools* falls back to HC0 for the whole fit; see the note (2026-11-18).

- [x] Give the tree-based methods the covariates as they appear in the model formula. `.make_covs_df()` in `R/functions_for_processing.R` builds them from `.covs` (the formula's covariates, with factors kept as factors) or, without it, from the model matrix, and `.add_missing_indicators_df()` adds missingness indicators to such a data frame (a factor's missing values become a `"<NA>"` level). `method = "bart"` and `method = "gbm"` use them for the trees, and gbm also assesses balance on them (with `.add_missing_indicators_df()`; `bal.init()` splits factors with `drop.first = "if2"`, so a two-level factor counts once, but an interaction in the formula contributes its components rather than itself); gbm's offset GLM still uses the model matrix. gbm splits an unordered factor by sorting its levels by the mean residual and taking the best split along that order (`EvaluateCategoricalSplit()`), so its weights are exactly invariant to level order; it treats an ordered factor as ordinal. `_dev/factor-coding.R` (results in `_dev/factor-coding.rds`) confirms this: gbm's weights are identical under permuted levels with the factor or dummies and change with integer codes, the factor balances at least as well as dummies, and bart's codings are invariant in distribution. `weightit.fit()` now accepts a data frame for `covs`, converted with `.process_covs_df()` to the model matrix `weightit()` builds and passed on as `.covs`; `weightitMSM.fit()` is unexported and only serves the joint MSM methods, so it was left alone. gbm's missing data: under `missing = "ind"`, gbm already fits with its native handling (each split sends missing values down a third branch of their own, which can be split further; this is not surrogate splitting), and the indicators are used only for balance, so neither `"surr"` nor a `"mia"` option was added. Fixed a pre-existing gbm bug: `use.offset = TRUE` with any missing covariate made the offset GLM fail; it now uses missingness indicators. With numeric covariates, gbm's weights are unchanged (checked on six configurations); they change with a factor of more than three levels or an interaction term. NEWS items added; the affected test files pass (2026-11-18).
